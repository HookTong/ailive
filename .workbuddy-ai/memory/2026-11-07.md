## 礼物动作列表装不下时自动上下滚

- `LiveOverview` 里给列表加了个 rAF 循环：滚到底停 0.7 秒 → 往回滚到顶 → 停 → 再往下，如此往复。内容没超出容器就什么都不做。
- 速度按「一遍扫完约 14 秒」换算（`max / 14`），再夹在 8~40px/s：溢出一点点不会慢到像没动，溢出很多也不会快得看不清。
- **最大的坑：Chrome 的 `scrollTop` 是整数**。`scrollTop += 0.13` 写回去会被直接抹掉，列表原地不动 —— 但每帧增量到 0.5px 以上时又会因为四舍五入而「动起来」，所以很容易误判成「逻辑没问题、只是慢」。必须自己维护一个浮点 `position` 累加，最后 `scrollTop = Math.round(position)`。最小复现：`el.scrollTop = 1.093` 读回来是 `1`。
- 另外两处细节：`dt` 钳在 0.064s（标签页切回来时 `now - last` 会很大，一下跳到列表底部）；用户自己滚过就 `Math.abs(scrollTop - position) > 2` 时把 position 同步过去，别硬拽。
- 尊重 `prefers-reduced-motion`：开了就不启动循环。
- effect 依赖用 `giftMotionRows.length` 而不是整个数组 —— 礼物触发动作会改 `characterStates`，跟着它重启会把滚动方向无谓地重置。每帧都重算 `max`，行高变化不需要重启。
- 实测（max=93，8px/s）：轨迹 `11 13 15 … 91 93 93 93 93 91 88 …`，触底停顿约 1s 后反向，实测速度 8.2px/s；不溢出时 `max=0`、`scrollTop` 恒为 0。
- `tsc -b --force` / `vite build` exit 0。

## 礼物动作改成队列，并让它压过说话动作

- 起因：`useLiveServer` 每 400ms 才 flush 一次，一个窗口里可能挤进好几条礼物。旧实现只认 feed 末尾那条 `latestGift`，其余全丢；而且 `activeMotion` 是状态不是队列，就算同时处理也会在同一帧互相覆盖。用户确认走「逐条排队播」的方案。
- 队列三支 effect：
  1. **入队**认 `douyinRoom.feed`：用 `queuedGiftIdRef` 记最大已入队 id，靠 id 单调递增挑出「这一批新来的」。断线重连时 `feed` 会被清零、事件序号从头开始，所以 `feed.length === 0` 时把 `queuedGiftIdRef` 也归零，否则新礼物会被当成旧的丢掉。礼物名走 `normalizeGiftName`（旧代码直接拿原始 `event.gift` 查配置，带空格或全角符号时查不到）。
  2. **出队**认 `giftTick`：没有 `playingGiftRef` 就取一条，`while (next && !giftMotions[next.name]) next = shift()` 跳过没配动作的礼物 —— 否则一条没配的礼物会白占 1.2 秒。
  3. **补漏**认 `characterStates`：播放窗口内 manifest 还没就绪的模型记进 `pendingModelsRef`，等它到位后趁这条礼物还在播补上。
- **播放窗口用 `setTimeout` 推进，绝不能放 effect 的 cleanup**。cleanup 每次依赖变化都会执行，会把「窗口结束」这个信号提前吃掉，队列直接卡死。卸载时另起一个 effect 清定时器。
- 优先级用 `motionHoldUntil` 时间戳（毫秒），不用布尔标志：说话可能持续好几秒，布尔标志没人负责清除，会永久锁死后续所有说话动作。礼物开播时写 `Date.now() + 1200`，`Live2D` 里 `speakingStarted` 触发 `speakMotion` 前比一下。
- **坑**：`applyModelProps` 里 `entry.motionHoldUntil = next.motionHoldUntil` 的赋值在判断之前，所以守卫必须读 `next.motionHoldUntil`，读 `entry` 拿到的是刚被覆盖的新值（正好是反的）。为了不踩这个坑，守卫值在赋值前就算好放进 `giftHolding`。
- 语义选择：窗口内开始说话，说话动作是**丢弃**而不是延后 —— `speakingStarted` 是边沿信号，没有可用的定时器去延后重放。要改成延后得再加一份 pending 状态。

### 验证方式（重要经验）

- **舞台字幕只反映 `activeMotion` 状态，看不到说话动作**：`speakMotion` 是 `Live2D` 内部直接调 `model.motion()`，不经过 React state，所以拿 DOM 观测说话动作永远为空。第一版测试就是这样误判的。
- 说话动作只能在运行时 hook `Live2DModel.prototype.motion` 或加临时探针。本次用后者：在 `speakingStarted` 分支临时 push `{group, blocked}` 到 `window.__motionProbe`，验证完立刻删掉（`grep __motionProbe src/` 确认无残留）。

## 试听时暂停外面音乐、关窗恢复原状

- 需求：弹窗里点 ▶ 试听时，外面的背景音乐要停；关掉弹窗后外面那首**接着原来的位置**放。
- 关键决定：**「扣下原 audio 元素」而不是「记下曲目再重建」**。`startSource` 每次换音源都新建元素，旧元素一旦没人引用就找不回来了 —— 位置、缓冲、`MediaElementSource` 连接全都白丢。所以 `beginPreview()` 把 `audioRef.current` 连同 `analyser` / `track` / `presetId` / `playing` 一起塞进 `previewBackupRef`，只 `pause()` 不销毁；`endPreview()` 把元素装回 `audioRef.current`，原来在放的就 `play()` 一下，**从原位置无缝续上**。
- `playing` 必须在 `pause()` **之前**读 —— `audio.paused` 是同步翻转的，晚一行就永远是 false。
- `beginPreview` 开头 `if (previewBackupRef.current) return`：StrictMode 下 effect 会跑 挂载→清理→挂载，不挡住的话第二次会把「已经记下的现场」覆盖成空的。
- `endPreview(restore = true)` 的 `restore` 参数是给「添加成功」这条分支用的：`addTrack` 已经 `startSource` 放了新曲目，关窗时**不能再把旧现场装回去**。`MusicModal` 用 `keepPlaybackRef` 记一下，卸载时传 `!keepPlaybackRef.current`。
- 装回去时 `audioRef.current !== backup.audio` 才 `pause()`：用户可能在弹窗里自己按过圆环播放（元素还是同一个），那是他的意思，别打断。
- 备份的元素早就 `loadedmetadata` 过了，不会再触发事件 → `setDuration` / `setCurrentTime` 得手动写回去，否则卡片上的时长一直停在 `--:--`。
- `reset()` 和卸载清理都要顺手 `previewBackupRef.current = null`（卸载还得 `?.audio?.pause()`，它可能不是 `audioRef` 指的那个），否则下次开窗会把已经清掉的现场又装回来。
- 实测（Playwright 打 `HTMLMediaElement.prototype.play/pause` 探针）：开窗前「正在播放 / 赛博 / 0:02」→ 开窗后「已暂停 / 赛博 / 0:02」且 1.3s 后时间仍是 0:02 → 试听变「星光 / 正在播放」→ 关窗回到「赛博 / 正在播放」，从 2.73s 续到 0:04；空开空关也照样续放。添加成功后关窗保持「测试曲」在放、胶囊也出来了。
- `tsc -b --force` / `vite build` 均 exit 0。

## 播放模式加「随机播放」

- `MusicLoopMode` 从 `'single' | 'list'` 扩成 `'single' | 'list' | 'shuffle'`，分段控件加第三项「随机播放」（四字和其它两项等长，三段各 85~86px 正好排满 259px，文字没截断）。
- 切歌只发生在 `ended` 里：`single` 由 `audio.loop` 兜着走不到；`list` 取 `(index + 1) % length`；`shuffle` 走新加的 `pickRandomTrack(list, index)`。
- **随机不能直接 `Math.random() * list.length`** —— 列表只有 5 首时连着放回同一首的概率是 20%，听起来就像随机坏了。改成偏移量取 `[1, length-1]`：`Math.floor(Math.random() * (list.length - 1)) + 1`，再 `(currentIndex + offset) % length`，天然排除自己。列表只有一首时只能还是它。
- 和列表循环一样，临时试听的音源（`index < 0`，不在列表里）仍然是「重头再放一遍」，没有下一首可接。
- 切到随机模式不会立刻跳歌 —— 它是「放完怎么接下一首」的规则，不是一次动作，和另外两项语义一致。
- 实测（把 `playbackRate` 拉到 16 倍让 35 秒的曲子 2 秒放完，采样 18 秒）：随机序列 `轻柔 → 雨声 → 轻柔 → 星光 → 雨声 → 星光 → 雨声 → 赛博`，7 次切换、4 首不同、**相邻重复 0 次**；切回列表循环是 `轻柔 → 赛博 → 雨声 → 专注 → 星光 → 轻柔`，顺序和首尾回绕都对。

## 舞台背景切换加交叉淡入淡出

- 原来是一个 div 直接换 `backgroundImage`，硬切。改成 `StageBackground` 组件，内部维护一个 `layers` 数组，每层一个绝对定位的 div。
- **关键是「旧图不淡出，新图淡入盖上去」**：旧图保持 `opacity: 1` 垫在下面，新图从 0 淡到 1，叠出来是 `a × 旧图 + (1-a) × 新图`，全程不透底色。要是两层同时一淡出一淡入，两边都半透明的那一瞬间会把 `.preview` 的渐变底透出来，看着像闪了一下。
- 新图**先 `new Image()` 预载再上屏**：淡到一半图才到的话会看到它「跳」一下。载入失败就保持旧图不动。
- 旧层什么时候卸：靠 `setTimeout(BACKGROUND_FADE_MS)` 而不是 `animationend` —— 动画被 `prefers-reduced-motion` 之类关掉时 `animationend` 不会来，层就永远卸不掉了。代价是 JS 的 `BACKGROUND_FADE_MS = 560` 必须和 scss 的 `$background-fade: 560ms` 手动对齐，两处都写了注释。
- 切「无背景」走另一条路：底下没有别的图可垫，整组原地淡出（`.stageBackgroundOut` 加在容器上）再清空。
- 每次换 url 先 `clearTimeout` 掉上一轮排着的卸载，否则它会把刚加进来的新图一起清掉；预载用 `cancelled` 标记，避免慢图在用户已经切走之后才上屏。
- 滤镜从「单张图」挪到容器上：两张图共用同一套参数，不会出现新旧图滤镜不一致。
- 实测（50ms 采样）：`默认@1` 全程不动，`bg_cinematic@0 → 0.16 → 0.39 → 0.75 → 0.93 → 1`，约 590ms 后旧层卸载、只剩一层；切「无背景」容器 opacity `1 → 0.92 → 0.77 → 0.35 → 0.11 → 0.04` 后清空；从「无背景」切回来是单层 0 → 1。连点四下（间隔 60ms）瞬时 5 层，1.4s 后收敛到 1 层且是最后点的那张，没有泄漏。

## 粒子特效 / 舞台滤镜加「固定 / 循环切换 / 随机切换」

- 需求原话是「加到 `展开细粒度控制` / `添加自定义滤镜` 按钮下面」—— 所以位置就是各块的最底部，和「舞台背景」那组三段控件对齐，三处视觉一致。
- 新增 `StageProvider/presets.ts`：`PresetRotateMode = 'fixed' | 'cycle' | 'random'`、`PRESET_ROTATE_OPTIONS`（固定 / 循环切换 / 随机切换）、`PRESET_ROTATE_INTERVAL_MS = 12_000`。间隔取和背景轮播同一个数 —— 三处切换频率不一样看着更乱。
- `pickNextIndex(length, currentIndex, mode)`：随机分支偏移量取 `[1, length-1]`（`Math.floor(Math.random() * (length - 1)) + 1`），天然排除自己。直接用 `Math.random() * length` 在 6 个滤镜上有 1/6 概率连着两次同一个，看起来就像「没切换」。
- `handleParticlePresetChange` / `handleFilterPresetChange` 改成 `useCallback`（依赖 `[particlePresetConfigs]` / `[customFilterPresets]`）。自动切换的 effect 依赖它们，每次渲染换新函数会让计时器永远重启 —— 表现是「切了一次就再也不切」。
- 自动切换的 effect 依赖里带当前预设：换完一次 effect 重跑、`setTimeout` 自然重新计时，手动点预设也会重置（不会「刚点完就被换走」）。不用 ref 存预设，就是为了让这层重置免费拿到。
- **关掉粒子 / 滤镜时整段跳过**（`!particleEnabled` 直接 return）：后台默默换预设，重新打开会看到一个自己没选过的效果。
- 滤镜侧顺手统一了胶囊选中态：原来 `active={preset === id}`，关掉滤镜后胶囊还亮着，和「无背景时清掉背景选中态」那条约定矛盾。现在和粒子一样写 `enabled && preset === id`；点胶囊本身仍会自动把开关打开（`handleFilterPresetChange` 里 `setFilterEnabled(true)`）。
- 实测（Playwright）：粒子「循环切换」在 12s 附近一跳；手动点「樱花」后 5.3s 仍是樱花、13.6s 变「萤火」；关掉 13s 预设不动、重新打开从当前继续。滤镜「循环」标准 → 电影 → 梦幻（12.4s / 24.3s），「随机」梦幻 → 标准 → 薄雾，相邻重复 0；粒子「随机」萤火 → 神经网络 → 花粉 → 银河，相邻重复 0。「重置舞台」后两处都回「固定」+ 默认预设（星尘 / 标准）。`pageerror` 为空，`tsc -b --force` / `vite build` 均 exit 0。
- **量测踩坑（两次都栽在这）**：`.chip:hover` 和 `.chip.active` 用的是同一个 `$accent-chip-fill`，点完鼠标还停在胶囊上，用「背景色 = 选中色」去读会一直读到那颗被点的，看上去像「自动切换停了」。读之前 `page.mouse.move(2, 2)` 再等 200ms（`$ease` 0.16s）。同理 `Switch` 是原生 checkbox + `role="switch"`，没有 `aria-checked` 属性，要用 `isChecked()`。

## 滚动条改成「指针进容器才显形」

- 第一版想当然写成 `&:hover::-webkit-scrollbar-thumb`，结果**完全不生效**。排查过程：无头 Chrome 压根不画滚动条（强制 `background: #ff0000 !important` 的对照组截出来也是空的），所以先误判成「CSS 没生效」；换 `headless: false` 后才看清 —— 无头/有头都验证了一遍：`matches(':hover')` 是 true，thumb 仍是 `transparent`；而给同一个元素加一个 class（`.sb-on`）立刻画出红条。结论：**Chromium 不会因为滚动容器的 `:hover` 变化重新解析 `::-webkit-scrollbar-thumb`**，只能靠 JS 换属性触发样式重算。
- 实现：`src/hooks/useHoverScrollbar` 在 `AppContent` 里调用一次，监听 `pointerover`，从 target 往上找最近一个「`overflow-y` 是 auto/scroll 且 `scrollHeight > clientHeight`」的祖先，给它挂 `data-scroll-hover`；`pointerout` 的 `relatedTarget` 为空（移出窗口）时清掉。`scroll-thin` 改成 `&[data-scroll-hover]::-webkit-scrollbar-thumb` 上色，8 个滚动容器（Drawer / Modal / Tabs / ScrollArea / 两个控制台 / GiftMotionCard / AiConfigDrawer）一行都不用改。
- **往上走遇到 `position: fixed` 要停**：弹窗的 `.backdrop` 是 fixed 且嵌在 `StageControlPanel` 的 DOM 子树里（Modal 没有 portal），不停的话指针停在弹窗上时底下的面板会一直露着滚动条。加了这条之后「弹窗打开、指针在遮罩上」实测 `on: false`。
- 6px 宽度一直保留（只是 `background: transparent`），显形时不会把内容挤一下 —— 实测 `clientWidth` 前后都是 249。
- 后来又按「不要紧贴列表」把轨道从 6px 放到 12px，滑块用 `border: 3px solid transparent` + `background-clip: padding-box` 缩回 6px，左右各留 3px 空隙。**写 `background` 简写会把 `background-clip` 重置成 `border-box`**，只能用 `background-color`。量测方式：临时写了个 40 行的 PNG 解码（`pwcheck/pngdecode.mjs`，zlib inflate + 逐行反滤波），DSF=4 截图后逐像素扫一条线 —— 实测滑块从第 60 像素到第 83 像素（6 CSS px），右侧留 12 像素（3 CSS px），与设计一致。
- 实测（`headless: false`）：动作预设列表 未进入 `attr=false` → 进入 `attr=true` → 移出 `attr=false`，右侧 8px 竖条的截图 idle 与 away 完全一致（`md5` 相同）、hover 不同；外观预设列表、抽屉 tabpanel 同样生效；`pageerror` 为空，`tsc -b --force` / `vite build` 均 exit 0。

## 滚动条让位：控制台左右留白对齐 + 胶囊与整宽按钮右边缘对齐

用户反馈两处：「调整滚动条后控制台的左右间距不一致，很多地方都变成了这样，弹幕指令列表也是这样」「按钮组容器中的按钮与下面的展开细粒度控制按钮的右侧也没对齐，其他类似的地方也一样」。

根因是同一件事：`::-webkit-scrollbar` 的 12px 是从容器 padding box 里切走的，内容区右侧凭空比左侧少 12px。旧代码在各处零散补了 `padding-right: 3px` / `4px`（6px 轨道时代的产物），现在轨道放到 12px 之后那些补丁全部变成额外偏移。

- 引入 `$scrollbar-size: 12px`（tokens.scss），`scroll-thin` 用它做轨道宽。
- 新增 `@mixin scroll-bleed`（`margin-right: -$scrollbar-size`）：把滚动条推进外层的右留白里，内容右边缘就能和同级整宽元素对齐。用在 9 处：`Drawer .scrollable`、`Modal .scrollable .body`、`Tabs .panel`、`GiftMotionCard .list`、`LiveChatCard .feed`、`StageControlPanel .backgroundPresets/.musicPresets`、`ParticleSetting .presets`、`FilterSetting .presets`、`VoiceSetting .presets`。
- 自己就是最外层的两个控制台则直接减 `padding-right`：`ModelControlPanel` / `StageControlPanel` 都用 `$pad-x: 24px` + `padding: ... ($pad-x - $scrollbar-size) ... $pad-x`，左右留白都是 24。`StageControlPanel` 的左右内边距原来是 20，一并改成 24 —— 20 - 12 = 8 < 12，嵌在里面的预设网格 bleed 12px 会顶出 4px 横向溢出。
- **关键补丁：`scroll-thin` 里加 `scrollbar-gutter: stable`**。第一版没加，结果 `VoiceSetting` 和背景预设这两个「内容没溢出」的网格反而比下方按钮突出去 12px（没有滚动条，却照样 bleed 了 12px）。加了之后不管溢不溢出都固定留 12px，让位基准才确定，顺带消掉「内容从放得下变要滚」时右边突然少 12px 的抖动。实测 Chrome 会按自定义 `::-webkit-scrollbar` 的宽度算 gutter。
- 带 `framed` 的 ScrollArea（动作 / 外观预设）**不 bleed**：可见的框才是对齐基准，滚动条留在框内，只把旧的 `padding-right: 4px` 删掉。
- 量测（1440×900，`headless: false`）：左面板 `[0,300]` pl=24 pr=12 cw=287，子元素统一 `[24,275]`；右面板 `[1140,1440]` 子元素 `[1165,1416]`，粒子网格 bleed 后边框盒 `[1165,1188]`、内容右边缘 1416 = 「展开细粒度控制」右边缘；抽屉 tabBar / 列表 / 说明文字右端全部 1418；弹窗 body 内容 `[463,977]` = actions 右边缘。全量扫描 `overflow-y: auto` 的元素，`scrollWidth > clientWidth` 一个都没有（没有横向滚动条）。
- 遗留：`AiConfigDrawer` 的「最近回复」`ul` 是「body 可滚 + 列表也滚」的双层结构，给它 bleed 会让 body 横向溢出 12px，所以没动它 —— 它的内容比上面的输入框窄 12px。`Tabs .panel` 已经 bleed，所以含 Tabs 的抽屉必须继续传 `scrollable={false}`，否则两层 bleed 叠起来也会横向溢出。

## 动作预设的选中行在框内居中

## 移除「说话触发动作」下拉，动作预设兼任说话动作

## 预设网格高度：正好 4 排，不多 1px

用户：「像这种滚动容器的最大高度应该刚好能容纳4排按钮而不会出现滚动条」。

量下来两处都不对：

| 外观 / 粒子 / 滤镜 / 背景 / 音乐（3 列，行距 5，无内边距） | 4 行 = 4×30+3×5 = **135** | 140 | 多 5px，只露出第 5 行的上边框，看着像被切了一截 |

## 滤镜开关重新打开要恢复关掉前的选中项

用户：「当舞台滤镜从禁用切换到启用应该恢复启用时的状态。现在切换回启用会重新选中『标准』，选中『标准』只应该是切回时旧的选中项被删除了导致无法命中才应该重新选中『标准』」。

根因在 `StageControlPanel` 传给 `FilterSetting` 的 `onEnabledChange`：

```tsx
if (enabled) handleFilterPresetChange('standard')   // ← 打开时无条件切「标准」
else setFilterEnabled(false)
```

当时大概是想「重新打开时把参数重新铺一遍」，但 `handleFilterPresetChange` 会**连选中项一起换掉**，于是用户关一下再开，选好的滤镜就没了、画面也回到原色。

改法：把开关语义收回 `StageProvider`，暴露的 `setFilterEnabled` 不再是裸 setter，而是 `handleFilterEnabledChange`：

- 关 → 只 `setFilterEnabledState(false)`，`filterPreset` 和 brightness/contrast/… 全部留着
- 开 → 选中项还在 `allFilterPresets` 里就只是打开；**指不到东西才** `handleFilterPresetChange('standard')` 兜底
- 顺手抽出 `applyFilterPreset(preset)`（只铺参数，不动开关和选中项），`handleFilterPresetChange` / `addCustomFilterPreset` / `removeCustomFilterPreset` 三处共用
- **`removeCustomFilterPreset` 不再走 `handleFilterPresetChange('standard')`** —— 那个会顺手 `setFilterEnabled(true)`，导致「滤镜关着的时候删掉一个自定义预设，开关自己弹回开启」。改成只 `setFilterPreset('standard') + applyFilterPreset(FILTER_PRESETS[0])`
- `handleFilterEnabledChange` 必须进 `value` 的 `useMemo` 依赖数组，否则 context 一直攥着首次渲染的闭包，里面的 `filterPreset` / `customFilterPresets` 都是旧的

实测（Playwright）：
- 选「霓虹」→ 关（`filter: none`、胶囊全灭）→ 开：仍选中「霓虹」，`filter = brightness(1.05) contrast(1.3) saturate(1.45) blur(0.2px)`
- 加自定义「临时滤镜」→ 关 → 删掉它：开关**保持关闭**；再打开 = 「标准」+ `brightness(1) contrast(1) saturate(1) blur(0px)`

顺带修正一条记错的老笔记：滤镜胶囊也是 `active={enabled && preset === id}`（关掉时整排都不亮），不是「只写 `preset === id`」。

## 卡片分类标题换成说人话的名字

用户给了 6 个标题：角色外观 / 角色音色 / 舞台背景 / 粒子特效 / 舞台滤镜 / 背景音乐（先给的「外观 / 音色」随即改成了「角色外观 / 角色音色」—— 模型那两项要带上「角色」，才和舞台那几项区分得开）。
