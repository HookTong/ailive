## 礼物动作列表装不下时自动上下滚

- `LiveOverview` 里给列表加了个 rAF 循环：滚到底停 0.7 秒 → 往回滚到顶 → 停 → 再往下，如此往复。内容没超出容器就什么都不做。
- 速度按「一遍扫完约 14 秒」换算（`max / 14`），再夹在 8~40px/s：溢出一点点不会慢到像没动，溢出很多也不会快得看不清。
- **最大的坑：Chrome 的 `scrollTop` 是整数**。`scrollTop += 0.13` 写回去会被直接抹掉，列表原地不动 —— 但每帧增量到 0.5px 以上时又会因为四舍五入而「动起来」，所以很容易误判成「逻辑没问题、只是慢」。必须自己维护一个浮点 `position` 累加，最后 `scrollTop = Math.round(position)`。最小复现：`el.scrollTop = 1.093` 读回来是 `1`。
- 另外两处细节：`dt` 钳在 0.064s（标签页切回来时 `now - last` 会很大，一下跳到列表底部）；用户自己滚过就 `Math.abs(scrollTop - position) > 2` 时把 position 同步过去，别硬拽。
- 尊重 `prefers-reduced-motion`：开了就不启动循环。
- effect 依赖用 `giftMotionRows.length` 而不是整个数组 —— 礼物触发动作会改 `characterStates`，跟着它重启会把滚动方向无谓地重置。每帧都重算 `max`，行高变化不需要重启。
- 实测（max=93，8px/s）：轨迹 `11 13 15 … 91 93 93 93 93 91 88 …`，触底停顿约 1s 后反向，实测速度 8.2px/s；不溢出时 `max=0`、`scrollTop` 恒为 0。
- `tsc -b --force` / `vite build` exit 0。

## 礼物动作改成队列，并让它压过说话动作

- 起因：`useLiveServer` 每 400ms 才 flush 一次，一个窗口里可能挤进好几条礼物。旧实现只认 feed 末尾那条 `latestGift`，其余全丢；而且 `activeMotion` 是状态不是队列，就算同时处理也会在同一帧互相覆盖。用户确认走「逐条排队播」的方案。
- 队列三支 effect：
  1. **入队**认 `douyinRoom.feed`：用 `queuedGiftIdRef` 记最大已入队 id，靠 id 单调递增挑出「这一批新来的」。断线重连时 `feed` 会被清零、事件序号从头开始，所以 `feed.length === 0` 时把 `queuedGiftIdRef` 也归零，否则新礼物会被当成旧的丢掉。礼物名走 `normalizeGiftName`（旧代码直接拿原始 `event.gift` 查配置，带空格或全角符号时查不到）。
  2. **出队**认 `giftTick`：没有 `playingGiftRef` 就取一条，`while (next && !giftMotions[next.name]) next = shift()` 跳过没配动作的礼物 —— 否则一条没配的礼物会白占 1.2 秒。
  3. **补漏**认 `characterStates`：播放窗口内 manifest 还没就绪的模型记进 `pendingModelsRef`，等它到位后趁这条礼物还在播补上。
- **播放窗口用 `setTimeout` 推进，绝不能放 effect 的 cleanup**。cleanup 每次依赖变化都会执行，会把「窗口结束」这个信号提前吃掉，队列直接卡死。卸载时另起一个 effect 清定时器。
- 优先级用 `motionHoldUntil` 时间戳（毫秒），不用布尔标志：说话可能持续好几秒，布尔标志没人负责清除，会永久锁死后续所有说话动作。礼物开播时写 `Date.now() + 1200`，`Live2D` 里 `speakingStarted` 触发 `speakMotion` 前比一下。
- **坑**：`applyModelProps` 里 `entry.motionHoldUntil = next.motionHoldUntil` 的赋值在判断之前，所以守卫必须读 `next.motionHoldUntil`，读 `entry` 拿到的是刚被覆盖的新值（正好是反的）。为了不踩这个坑，守卫值在赋值前就算好放进 `giftHolding`。
- 语义选择：窗口内开始说话，说话动作是**丢弃**而不是延后 —— `speakingStarted` 是边沿信号，没有可用的定时器去延后重放。要改成延后得再加一份 pending 状态。

### 验证方式（重要经验）

- **舞台字幕只反映 `activeMotion` 状态，看不到说话动作**：`speakMotion` 是 `Live2D` 内部直接调 `model.motion()`，不经过 React state，所以拿 DOM 观测说话动作永远为空。第一版测试就是这样误判的。
- 说话动作只能在运行时 hook `Live2DModel.prototype.motion` 或加临时探针。本次用后者：在 `speakingStarted` 分支临时 push `{group, blocked}` 到 `window.__motionProbe`，验证完立刻删掉（`grep __motionProbe src/` 确认无残留）。

## 试听时暂停外面音乐、关窗恢复原状

- 需求：弹窗里点 ▶ 试听时，外面的背景音乐要停；关掉弹窗后外面那首**接着原来的位置**放。
- 关键决定：**「扣下原 audio 元素」而不是「记下曲目再重建」**。`startSource` 每次换音源都新建元素，旧元素一旦没人引用就找不回来了 —— 位置、缓冲、`MediaElementSource` 连接全都白丢。所以 `beginPreview()` 把 `audioRef.current` 连同 `analyser` / `track` / `presetId` / `playing` 一起塞进 `previewBackupRef`，只 `pause()` 不销毁；`endPreview()` 把元素装回 `audioRef.current`，原来在放的就 `play()` 一下，**从原位置无缝续上**。
- `playing` 必须在 `pause()` **之前**读 —— `audio.paused` 是同步翻转的，晚一行就永远是 false。
- `beginPreview` 开头 `if (previewBackupRef.current) return`：StrictMode 下 effect 会跑 挂载→清理→挂载，不挡住的话第二次会把「已经记下的现场」覆盖成空的。
- `endPreview(restore = true)` 的 `restore` 参数是给「添加成功」这条分支用的：`addTrack` 已经 `startSource` 放了新曲目，关窗时**不能再把旧现场装回去**。`MusicModal` 用 `keepPlaybackRef` 记一下，卸载时传 `!keepPlaybackRef.current`。
- 装回去时 `audioRef.current !== backup.audio` 才 `pause()`：用户可能在弹窗里自己按过圆环播放（元素还是同一个），那是他的意思，别打断。
- 备份的元素早就 `loadedmetadata` 过了，不会再触发事件 → `setDuration` / `setCurrentTime` 得手动写回去，否则卡片上的时长一直停在 `--:--`。
- `reset()` 和卸载清理都要顺手 `previewBackupRef.current = null`（卸载还得 `?.audio?.pause()`，它可能不是 `audioRef` 指的那个），否则下次开窗会把已经清掉的现场又装回来。
- 实测（Playwright 打 `HTMLMediaElement.prototype.play/pause` 探针）：开窗前「正在播放 / 赛博 / 0:02」→ 开窗后「已暂停 / 赛博 / 0:02」且 1.3s 后时间仍是 0:02 → 试听变「星光 / 正在播放」→ 关窗回到「赛博 / 正在播放」，从 2.73s 续到 0:04；空开空关也照样续放。添加成功后关窗保持「测试曲」在放、胶囊也出来了。
- `tsc -b --force` / `vite build` 均 exit 0。

## 试听改成独立播放器：舞台卡片不再被带跑 / 选本地文件即播 / 关窗清空

- 三个诉求，根因是同一个：试听借用了主播放器，所以 `track` / `currentTime` / `duration` / `analyser` 被改，舞台那张卡片跟着变。
  1. 外面（舞台）的「正在播放」卡片不能随试听变；
  2. 选完本地文件要立刻播，不该再点一次 ▶；
  3. 弹窗每次关闭都要清掉试听卡片的信息。
- **改法：`MusicProvider` 里加一套完全独立的试听播放器**（`previewAudioRef` + `previewTrack/Playing/CurrentTime/Duration/Analyser`），上下文里打包成 `preview: MusicPreview`（`track / playing / currentTime / duration / analyser / start / toggle / clear`）。原来的 `previewUrl` 删掉，`MusicModal` 不再收 `onPreview`，直接从 `useMusic()` 拿 `preview`。

- 频谱那段（`createMediaElementSource` + `createAnalyser`）抽成 `attachAnalyser(audio, url)`，主播放器和试听共用，`startSource` 少 18 行。
- 选本地文件即播：`handleFile` 里直接 `void playPreview(objectUrl, 文件名去扩展名)`。名字走 `file.name.replace(/\.[^.]+$/, '')`，卡片上显示「ADXXX」而不是「ADXXX.wav」或「本地音乐」。试听名优先级：显式传入 > 列表里同 url 的 label > `displayName(url)`。
- 关窗清空：`endPreview` 里先 `stopPreview()` 再决定要不要恢复外面的播放，所以 `endPreview(false)`（刚添加成功那条）也会清。空卡片文案是 `等待试听 / 尚未选择音乐 / 0:00 / --:--`，没有可播内容时不传 `onToggle`，圆环退回纯装饰。

## 顺手修：重置舞台后卡片残留上一首的秒数

- 现象：点「重置舞台」，卡片变成「已暂停 / 轻柔 / **0:03** / --:--」—— 标题和时长都重置了，秒数没重置。
- 原因：`timeupdate` 大约 4Hz，`pause()` 之后还会有一个**已排队**的事件在 `setCurrentTime(0)` 之后才送达；处理函数里 `previous` 是 0、`audio.currentTime` 还是旧值，于是又把旧秒数写了回去。
- 改法：给 `loadedmetadata` / `timeupdate` 加一个 `isCurrent = () => audioRef.current === audio` 的守卫（试听播放器同样处理）。`play` / `pause` **不加**守卫 —— 它们本来就会被新元素的同名事件覆盖，挡住反而会在「新音源被自动播放策略拦下」时留下一个假的「正在播放」。
- 实测：重置后是「已暂停 / 轻柔 / 0:00 / --:--」。

## 播放模式加「随机播放」

- `MusicLoopMode` 从 `'single' | 'list'` 扩成 `'single' | 'list' | 'shuffle'`，分段控件加第三项「随机播放」（四字和其它两项等长，三段各 85~86px 正好排满 259px，文字没截断）。
- 切歌只发生在 `ended` 里：`single` 由 `audio.loop` 兜着走不到；`list` 取 `(index + 1) % length`；`shuffle` 走新加的 `pickRandomTrack(list, index)`。
- **随机不能直接 `Math.random() * list.length`** —— 列表只有 5 首时连着放回同一首的概率是 20%，听起来就像随机坏了。改成偏移量取 `[1, length-1]`：`Math.floor(Math.random() * (list.length - 1)) + 1`，再 `(currentIndex + offset) % length`，天然排除自己。列表只有一首时只能还是它。
- 和列表循环一样，临时试听的音源（`index < 0`，不在列表里）仍然是「重头再放一遍」，没有下一首可接。
- 切到随机模式不会立刻跳歌 —— 它是「放完怎么接下一首」的规则，不是一次动作，和另外两项语义一致。
- 实测（把 `playbackRate` 拉到 16 倍让 35 秒的曲子 2 秒放完，采样 18 秒）：随机序列 `轻柔 → 雨声 → 轻柔 → 星光 → 雨声 → 星光 → 雨声 → 赛博`，7 次切换、4 首不同、**相邻重复 0 次**；切回列表循环是 `轻柔 → 赛博 → 雨声 → 专注 → 星光 → 轻柔`，顺序和首尾回绕都对。
- `tsc -b --force` / `vite build` 均 exit 0。

## 「无背景」时背景胶囊不该留着选中态

- 现象：选了「无背景」，台上确实空了，但背景胶囊里上一次那张（如 Lo-fi）仍然整颗绿色高亮 —— 看起来像「既没背景又选了 Lo-fi」。
- 原因：`backgroundUrl` 在选「无背景」时是**故意留着**的（切回「固定」要接着用上次那张），所以 `active={backgroundUrl === url}` 照样命中。
- 改法：选中态改成跟着「台上到底有没有背景」走 —— `active={backgroundMode !== 'none' && backgroundUrl === url}`。`backgroundUrl` 本身不动，所以点任意一张胶囊时 `selectBackground` 里那句 `if (backgroundMode === 'none') setBackgroundMode('fixed')` 照旧把它切回「固定」，胶囊立刻重新亮起。
- 顺手补 `PresetChip` 的 `aria-pressed={active}`：`Button` 的 `active` 只加了个 CSS 类，读屏用户完全摸不到选中态。三处预设列表（背景 / 滤镜 / 音乐）一起受益。
- 实测（Playwright，`role="radio"` 取分段控件 —— `Segmented` 用的是 `role="radiogroup"` + `role="radio"`，不是 button）：初始 `默认 pressed` / 模式「固定」→ 点「无背景」后**五个胶囊 `aria-pressed` 全 false** / 模式「无背景」/ 舞台只剩星空 → 点回 Lo-fi，Lo-fi `pressed` / 模式「固定」/ 背景图恢复。`pageerror` 为空。
- `tsc -b --force` / `vite build` 均 exit 0。
