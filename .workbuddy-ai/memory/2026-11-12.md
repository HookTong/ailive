## 排查「拉取初始帧失败（返回空响应）」

- 用户报错截图：房间 764416793518，提示「拉取初始帧失败（返回空响应）。常见原因：房间未开播、cookie 失效、或被风控」。
- 先排掉「没开播」：`get_live_info` 正常，`room_status = 2`（直播中），标题也拿到了。
- 复现 `fetch_initial_frame`：两次都是 `200` + `len=0` + `content-type: application/json`，响应头带
  `x-vc-bdturing-parameters: {"code":"10000","type":"verify","subtype":"slide"}` —— **风控要滑块验证**。
- 变量法定位（同一份 ttwid）：
  | 请求 | 结果 |
  | --- | --- |
  | 全量 cookie | 0 字节，slide/verify |
  | 只带 ttwid | **61KB protobuf** |
  | 只带 sessionid* | 0 字节，slide/verify |
  | 去掉 sessionid*（保留其余登录字段） | 仍 0 字节 |
  | 换页面新下发的 ttwid + 全量 cookie | 仍 0 字节 |
  → 结论：**只要请求里出现登录态 cookie 就被拦**，跟 ttwid / msToken / 房间无关。
- 又验了 WS：初始帧用匿名拿、WS 带全量 cookie 照样收 58 条事件 —— 只有取初始帧这一步敏感。
- 修复：`Auth.guest_cookie`（只 `ttwid` + `msToken`）+ `fetch_initial_frame` 改成「匿名/登录 × 不带/带 a_bogus」四次尝试，匿名优先；
  新增 `_needs_verify()` 读 `x-vc-bdturing-parameters`，被拦时给出「是风控不是没开播」的明确报错。
  `get_live_info` 顺手把页面下发的 ttwid 写回 auth，后续请求用最新设备票据。
- 验证：真实 cookie 端到端 20 秒收到 44 条（进场/弹幕/点赞/礼物/房间）；`python -m dy.main --port 8788` 起一份新桥接，SSE 依次 connecting → room → live 并有 event 推送。

## 排查「开自然语言控制 + 弹幕刷屏 → token 爆增」

- 根因：**理解那条链路没有全局节流**。回复有 `MIN_REPLY_INTERVAL_MS`（6s），理解只有「每人 3s」+「队列最多 4 条」，
  队列一空就继续，实际速度 = 模型响应速度（≈1 次/秒）。而每次理解都要重发一份和弹幕长短无关的大 prompt：
  27 个工具定义 ≈1900 token（`buildActionTools` 实测 JSON 4788 字符）+ 状态快照 ≈260 + 系统提示 ≈150 ≈ **2300 token/次**。
  刷屏 1 条/秒 → 每分钟十几万 token。
- 次要因素：同文本缓存只认「一字不差」；队列满时转普通回复（又花一次回复的钱，但被 6s 节流兜住）；多人刷屏时每人 3s 冷却形同虚设。
- 改法（`AiChatProvider`）：
  - `MIN_ROUTE_INTERVAL_MS = 2000` 全局最小间隔，`waitForRouteSlot()` 只在真打接口前等；命中缓存不占名额。
  - `noteChat()` 记弹幕到达时间并返回是否刷屏；`FLOOD_WINDOW_MS = 10s` / `FLOOD_CHAT_THRESHOLD = 25` 命中就不送模型。
    顺序是「先判密度、再判 `allowRoute`」—— 刷屏期间不该消耗观众的指令额度。
- 实测（Playwright + mock ark，`nl-flood.mjs`）：6 秒 60 条弹幕，理解调用从改前 ≈60 次压到 **6 次**，间隔精确 2000ms；
  正常节奏 3s 一条 × 6 条仍然 **6/6 全部理解**（间隔 2.8–3.2s）。
- `nl-flood-command.mjs`：刷屏中间夹 `[音乐|播放]`，音乐照常播放（4/4），确认方括号指令不受刷屏判定影响。
- `tsc -b --force` + `vite build` 通过。

## 自然语言控制改成 `[AI控制]` 前缀触发

- 用户要求：只有发 `[AI控制]+$自然语言` 才请求 AI 理解，其它弹幕一律不调模型。
- `data/actions.ts` 新增 `parseAiControl`（正则 `/^\[\s*AI\s*控制\s*\]/i`，忽略大小写和括号内空格），返回剥掉前缀后的话；
  不是这个前缀返回 `null`，只有前缀返回空串。**前缀不进 `ACTIONS`** —— 它没有可执行的东西，`looksLikeCommand` 也认不出它，两边不打架。
- `AiChatProvider` 的 feed 循环：`looksLikeCommand` 之后接 `parseAiControl`。命中就把 `{...item, text: aiText}` 入队（**缓存键、播报、失败回退用的都是剥掉前缀的那句**）；
  空内容整条 `continue`；关掉 / 冷却中也 `continue`，不落普通回复。
- **删掉上一轮加的刷屏判定**（`noteChat` / `FLOOD_WINDOW_MS` / `FLOOD_CHAT_THRESHOLD`）：它按「总弹幕密度」算，加了前缀之后会误伤 —— 忙房间里少数几条 `[AI控制]` 会被无差别挡掉。
  成本上限交给 `MIN_ROUTE_INTERVAL_MS`（2s，30 次/分钟）就够。
- 文案三处一起改：`AiConfigDrawer` 的开关说明、`ChatCommandSetting` 的开头段落、`ChatCommandCard` 的提示句。
  速查卡**没有**新增一行 —— 卡片已经顶到 540px 上限，加一行会把最后一条 Tag 裁掉（实测列表溢出 25px），所以把 `[AI控制]` 并进顶部那句说明里，卡片高度保持 516px 不变。
- 实测（`ai-prefix.mjs`，mock 方舟）：30 条无前缀刷屏 + 2 条无前缀闲聊 → **0 次理解**；`[AI控制]换个赛博背景` → 1 次，背景真的切到「赛博」；
  `[AI控制]` 空内容 → 不请求也不回复；送模型的文本是「观众说：「换个赛博背景」」。6/6 通过。
- `tsc -b --force` + `vite build` 通过；深浅主题截图确认速查卡与 AI 抽屉排版正常。

## 排查「一个人被回复后，后面十几条全没反应」

- 现象：同一个人 3~4 秒一条，被回一句之后中间全静默，要「隔很久」才再被回；弹幕没刷屏。
- 根因：`CHAT_USER_COOLDOWN_MS = 45_000`。冷却在 `enqueue` 里按 `chat:<昵称>` 记，命中就直接 `return` —— 队列进不去、不调模型、不说话。
  3.5 秒一条 → 45 秒里约 13 条被静默吞掉。**不是丢了弹幕，是主动挡掉**。
- 复现脚本 `one-user-cooldown.mjs`（`pwcheck`，需 `createRequire` 指到 npx 缓存里的 playwright）：
  同一个人 18 条 → **2 次回复，间隔精确 45.0s**；换成 18 个不同的人同样节奏 → **10 次**。差值 8 条全是冷却吃掉的。
- 改法（`AiChatProvider`）：
  - `CHAT_USER_COOLDOWN_MS` 45s → **6s**（等于 `MIN_REPLY_INTERVAL_MS`）。关键认识：**总闸是全局节流，改小每人冷却不会多花 token，只决定名额分给谁**。
  - 新增「队列里已经有这个人的 chat 就先不加」——「一个人连发占满队列」交给这一条挡，比按时间窗屏蔽精确得多，且不影响他后续正常发言。
  - `pushQueue` 改成返回「这条是否还在队列里」，冷却和同文本时间戳**只在真入队后才写**：被上限挤掉的那条没被回复，不该消耗观众额度。
  - `SAME_TEXT_WINDOW_MS` 60s → 30s：短句全站一分钟只答一次太伤（观众会觉得没人理）。
  - `AiConfigDrawer` 的自动回复说明补「一条说完才轮到下一条」，解释为什么不是每条都回。
- 复测：同一个人 18 条 → **9 次回复，间隔 7.0s**（受 6s 节流 + 说话时长限制），对照组 10 次，只差观察窗尾部那一条。
- 回归：`ai-prefix.mjs` 6/6 通过（`[AI控制]` 门控没受影响）；`nl-flood.mjs` 的「6 条都理解」断言已过时（无前缀不再送模型），理解 0 次是正确行为。
- `tsc -b --force` + `vite build` 通过。
